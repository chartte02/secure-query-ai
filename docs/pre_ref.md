新的安全风险

| 用户身份 | 自然语言问题 |

因此，我们关注的核心问题是：

如何在保留自然语言查询便利性的同时，确保模型生成的 SQL 不会突破数据库权限边界？

## 第三部分：核心安全机制与攻防案例

### 第 8 页：SQL Security Gateway 的核心实现

全场重点

PPT 展示：

建议使用以下流程：

输入：候选 SQL + 可信 Actor

SQLGlot AST Parser

解析 SQL 语法树，识别语句类型和结构

Policy Engine

单语句 / 只读 / 表白名单 / 列权限 / Schema 版本

## ALLOW

允许执行

## MASK

受控脱敏

## BLOCK

拒绝执行

Real Gateway

可信身份映射 / hardened 数据库 / 只读事务 / 限行

审计记录 + 脱敏结果

代码重点：

- `sql_policy`
- `real_gateway`
- `audit_writer`

讲解词：

这一页是整个项目的核心。

我们设计了一个独立的 SQL Security Gateway。

它接收模型生成的 SQL 和可信用户身份，首先使用 SQLGlot 将 SQL 转换为 AST，也就是抽象语法树。

为什么不直接用正则表达式？

因为 SQL 语法比较复杂，同一个查询可能有不同的写法。单纯依靠字符串匹配容易遗漏嵌套查询、别名和复杂表达式。

解析 AST 后，网关会执行一系列确定性规则检查。

例如，是否只有一条 SQL 语句，是否属于只读操作，是否访问了允许的表和列，以及 Schema 版本是否匹配。

随后形成三种决策：

ALLOW 表示允许执行；MASK 表示需要进行受控脱敏；BLOCK 表示直接阻断。

通过检查之后，Real Gateway 会使用可信身份映射出的数据库角色连接 hardened 实例，在只读事务中执行查询，并限制返回行数。

最后，审计模块记录安全决策和原因。

这里最重要的是：安全决策由确定性代码完成，而不是让大语言模型自己判断是否安全。

### 第 9 页：核心攻防案例一——跨用户越权读取

PPT 展示：

攻击场景：

- 当前身份：学生 A
- 目标数据：学生 B 的成绩
- 攻击目的：读取其他用户不允许访问的数据

攻击 SQL 示意：

```
SELECT *
FROM academic.student_scores;
```

对照结果：

baseline

可能越权读取

弱防护环境中，宽泛读取可能暴露其他学生的数据。

hardened

权限约束

通过 RLS、数据库角色和网关策略限制可见数据范围。

讲解词：

第一个案例是跨用户越权读取。

在正常业务中，学生只能查询自己的成绩。

但是，如果模型生成了一个没有正确限制用户身份的 SQL，例如直接读取整个成绩表，那么在权限配置不充分的情况下，就可能返回其他学生的成绩。

我们将这一场景放到 baseline 和 hardened 两种环境中进行对比。

baseline 故意采用较宽松的读取权限，可以观察到越权访问的风险。

hardened 则结合网关策略和 PostgreSQL 的 RLS，让数据库根据可信角色限制实际能够访问的数据行。

这里的关键是，即使模型生成了越权 SQL，也不能直接获得全部数据。

### 第 10 页：核心攻防案例二——敏感列读取与身份伪造

PPT 展示：

两个攻击场景：

COL-01：敏感列读取

```
SELECT *
FROM academic.students;
```

攻击目的：获取不应该暴露的敏感字段。

防御：

- 列级权限
- 安全视图
- MASK 脱敏策略

DPI-01 / IPI-01：身份与提示词攻击

攻击目的：

- 伪造用户身份或请求上下文。
- 通过数据库中存储的恶意内容影响模型行为。

讲解词：

第二组案例主要关注敏感字段泄露和身份信任问题。

首先是敏感列读取。

有些信息即使属于同一张业务表，也不应该对所有用户开放。例如身份认证信息、联系方式等。

因此，我们通过列级权限、安全视图和脱敏策略限制敏感字段的读取。

另一个问题是身份伪造。

如果系统直接信任用户请求中传入的身份信息，那么攻击者可能通过修改参数，冒充其他用户进行查询。

所以我们需要让身份由可信的服务端上下文确定，而不是由模型或用户随意指定。

此外，我们还研究了间接 Prompt Injection。攻击者可以将恶意指令放进数据库的 course_feedback 等内容中。当模型后续读取这些内容时，可能受到其中指令的影响。

这说明数据库中的文本内容也不能被当成可信的系统指令。

### 第 11 页：核心攻防案例三——间接 Prompt Injection 与危险 SQL

PPT 展示：

## 间接 Prompt Injection 攻击链

① 恶意内容写入

攻击者将恶意指令植入 course_feedback

② 模型读取数据库内容

反馈文本进入模型上下文

③ 恶意指令影响 SQL 生成

尝试诱导模型生成非预期查询

④ 独立网关执行策略检查

阻断不符合权限和只读策略的 SQL

危险 SQL 示例：

```
DELETE FROM academic.student_scores
WHERE student_id = 'student_a';
```

讲解词：

这一页介绍项目中比较有代表性的间接 Prompt Injection 攻击。

与直接向模型输入恶意指令不同，间接注入是把恶意内容藏在模型可能读取的数据中。

例如攻击者在课程反馈中写入一段伪装成系统指令的内容。

当模型后续查询课程反馈并将其放入上下文时，这段恶意文本可能影响模型的行为，使其生成偏离用户原始意图的 SQL。

我们要说明的是，模型是否真的被成功诱导，需要通过具体实验记录来验证，不能仅凭恶意文本存在就认定攻击成功。

此外，项目还设计了 DELETE 等危险操作的实验。

例如删除学生成绩的 SQL，即使语法完全正确，也不应该通过只读查询网关。

因此，我们从 SQL 操作类型和数据库事务两个层面进行防护，避免危险语句进入正式数据环境。

### 第 12 页：安全策略如何对应攻击？

PPT 展示：

建议做成一张攻击—防御映射表。

| 攻击编号 | 攻击目标 | 对应防御 |
| --- | --- | --- |
| ROW-01 | 跨用户读取数据 | RLS、可信身份 |
| COL-01 | 读取敏感字段 | 列权限、脱敏视图 |
| DPI-01 | 身份或上下文伪造 | 可信 Actor 映射 |
| IPI-01 | 间接 Prompt Injection | 不信任数据内容、SQL 网关 |
| W-01 | 非法写入 | 只读事务、角色权限 |
| SQL-01 | 危险 SQL / 多语句 | AST 策略校验 |

讲解词：

前面介绍了几种攻击方式，这一页将它们和防御机制对应起来。

ROW-01 主要通过 RLS 和可信身份解决行级越权问题。

COL-01 通过列级权限和脱敏视图保护敏感字段。

DPI-01 主要解决身份上下文不可信的问题。

IPI-01 则强调不能信任数据库中的自然语言内容，模型生成的 SQL 必须重新经过独立验证。

W-01 通过只读事务和数据库角色限制写操作。

SQL-01 则通过 SQL AST 解析和策略检查限制危险语句。

这里可以总结为三层：

1. 模型输入和生成层：降低 Prompt Injection 风险。
2. SQL 网关层：进行确定性的语法和策略校验。
3. 数据库层：使用 PostgreSQL 权限机制进行最终强制执行。

# 五、非常重要：汇报时需要注意的实现边界

我重新核对了你目前 GitHub 的 README 和 2026-11-03 的 `docs/status.md`，有几个地方建议在 PRE 中准确表达，避免老师追问时出现技术描述不一致。

需要特别注意

1. 正式网关与实验室直连不是一回事。

当前 `/api/v1/queries` 默认返回 `503 unavailable`，必须显式设置 `SECUREQUERY_FORMAL_GATEWAY=true` 才启用正式网关。

`lab_direct` 是隔离实验室演示执行器，不具备 C 正式网关的完整策略功能。不能把实验室直连的结果说成正式网关的验收结果。

2. 模型拒答与系统阻断不是一回事。

模型拒答属于 AI 层的防御；网关 BLOCK 属于安全策略层的防御；数据库 SQLSTATE 错误或 RLS 过滤则属于数据库层的结果。

4. 不要把所有攻击都说成由 SQL 网关阻断。

例如跨学生查询可以被网关允许，但最后由 RLS 返回零行。这恰好体现了多层防御的意义。

讲解词：

首先介绍一下我们的研究背景。

传统数据库系统通常要求使用者了解数据库结构，并掌握 SQL 语法。例如，要查询某个学生的成绩，需要知道成绩表、学生表之间的关系，以及对应的字段。

随着大语言模型的发展，我们可以直接通过自然语言提出问题，让模型自动理解用户意图、获取数据库结构，并生成 SQL。

这种方式降低了数据库的使用门槛，但同时也改变了数据库的访问方式。

过去，用户通常直接编写 SQL；现在，用户的自然语言会先影响模型的行为，再由模型生成 SQL，最后通过应用程序连接数据库执行。

这里出现了一个新的信任问题：模型是否能够准确区分正常查询意图和恶意指令？它生成的 SQL 是否符合当前用户的实际权限？

因此，我们将研究重点确定为三个问题：自然语言和不可信数据如何影响 SQL 生成；不同层次的安全机制分别能解决什么问题；以及防御措施会对安全性和正常查询能力产生怎样的影响。

这三个问题也构成了后面整个项目的研究主线。

讲解词：

结合前面的论文和案例，我们进一步整理了系统的威胁模型。

攻击者不一定需要掌握 SQL，只需要能够向 AI 数据库助手提出问题，或者向系统中提交一些后续可能被模型读取的文本。

## 第 7 页：现有防御技术调研与局限

从调研过渡到技术方案的关键页

PPT 标题：现有安全机制能解决什么？还有什么不足？

建议做成一张比较表：

| 防御机制 | 可以解决的问题 | 主要局限 |
| --- | --- | --- |
| Prompt 安全约束 | 降低恶意 SQL 生成概率 | 不能作为确定性安全边界 |
| 参数化查询 | 防止参数值改变 SQL 结构 | 不能判断整条模型 SQL 是否越权 |
| SQL AST 检查 | 识别语句类型、访问对象 | 需要正确配置业务授权策略 |
| RBAC | 控制用户和角色的操作权限 | 表级权限不能直接表达所有行级业务规则 |
| RLS | 限制可见数据行 | 身份映射错误、owner 或绕过 RLS 的角色可能破坏预期 |
| 列级权限 | 限制敏感字段访问 | 需要避免通过其他视图或基表路径绕过 |
| 只读事务 | 阻止写入操作 | 不能阻止所有敏感数据读取 |

下方总结：

研究结论

没有任何单一机制可以覆盖整个攻击链。需要将模型行为约束、SQL 执行前授权和数据库原生权限结合起来。

讲解词：

在确定攻击模型之后，我们进一步调研了现有防御机制。

首先是 Prompt 安全约束。

我们可以在系统提示词中告诉模型，只能查询当前用户有权限访问的数据，禁止生成 DELETE 和 DROP 等操作。

但是，Prompt 本质上是对模型行为的引导，而不是强制访问控制机制。模型可能因为恶意输入、上下文污染或者自身生成错误而违反这些约束。

其次是参数化查询。

参数化查询可以有效防止用户输入的参数值被当成 SQL 代码，但它并不能判断模型生成的一整条 SQL 是否符合业务权限。

例如，SQL 本身没有任何注入语法问题，但它可能合法地查询了其他学生的成绩。

然后是 SQL AST 检查。我们可以在执行前解析 SQL，检查是否包含多条语句、是否访问了不允许的表或列、是否属于写操作。

在数据库层面，我们重点研究 PostgreSQL 的三类能力。

RBAC 负责角色和操作授权；RLS 负责行级访问限制；列级权限负责限制敏感字段。

只读事务可以进一步阻止写操作。

但是，数据库权限同样需要正确绑定用户身份。如果所有应用用户共用一个权限过大的连接账号，或者错误使用数据库所有者身份，那么原本期望的权限隔离就可能失效。

因此，我们认为这些机制应该互相补充，而不是相互替代。

## 第 8 页：调研总结——为什么最终选择分层防御？

PPT 标题：从调研结论到 SecureQuery AI 的设计

## 第一层：LLM / Prompt

降低模型生成恶意 SQL 的概率

## 第二层：SQL Security Gateway

SQLGlot AST / 确定性策略 / ALLOW · MASK · BLOCK / 审计

## 第三层：PostgreSQL

RBAC / RLS / Column Permissions / Read-only Transaction

PPT 下方放三个研究问题：

- RQ1：攻击能否改变实际执行的 SQL？
- RQ2：网关和数据库能否独立阻止攻击？
- RQ3：安全性提高之后，正常查询能力是否受到影响？

讲解词：

通过前面的市场、开源项目、学术论文和安全案例调研，我们最终形成了一个核心认识：

不能把模型当成可信的数据库访问控制主体。

模型应该负责理解用户问题和生成候选 SQL，但不应该拥有决定自己能否访问数据的权力。

因此，我们设计了三层防御。

第一层是模型和 Prompt，主要降低恶意 SQL 生成的概率。

第二层是独立 SQL 安全网关，在执行之前解析 SQL，并根据可信身份、表列权限和操作类型做出确定性决策。

第三层是 PostgreSQL，通过 RBAC、RLS、列级权限和只读事务，确保即使模型或者网关上游出现问题，数据库仍然能够提供最终的权限约束。

我们的研究并不是提出一种全新的数据库权限算法，而是把已有的 AI 安全研究、SQL 解析技术和数据库原生权限机制结合起来，构建一套可以进行攻击复现、分层对照和效果评估的实验系统。

接下来就介绍我们如何把这些调研结论转化为 SecureQuery AI 的具体实现。

通过这样的设计，我们可以尽量分离不同防御机制的贡献。

例如，E1 和 E0 的对比主要用于观察 Prompt 的作用；E2 和 E1 的对比用于观察网关的作用；E3 和 E0 的对比用于观察数据库权限的作用；E4 则验证整体组合效果。

评价时，我们不只看模型有没有拒绝攻击，还看最终有没有真正读取到未授权数据，以及有没有成功修改数据库。

同时，我们也必须考虑正常查询是否受到影响。

因为一个完全拒绝所有查询的系统虽然很难发生数据泄露，但它也失去了自然语言数据库助手的实际价值。

因此，安全性和可用性必须同时评价。

GitHub+1

# 四、建议补充的调研内容：哪些值得进一步完善？

现有四份调研材料已经足以支撑 PRE，但如果想让老师感觉到你们做了比较深入的研究，我建议补充三个方向。

## 1. 补充 Text-to-SQL 的技术发展脉络

目前的市场调研主要介绍产品，可以增加一张技术发展图。

1. 传统 Text-to-SQL
    
    自然语言 → SQL 生成
    
    核心问题：如何把问题转换为正确的 SQL。
    
2. Schema-aware Text-to-SQL
    
    自然语言 + Schema + Few-shot 示例 → SQL
    
    核心问题：如何理解表结构、字段含义和业务关系。
    
3. RAG / 语义增强 Text-to-SQL
    
    自然语言 + Schema 检索 + 业务术语 → SQL
    
    核心问题：检索内容是否准确可信，是否可能受到数据污染。
    
4. Agentic Text-to-SQL
    
    模型自主调用 Schema、查询、执行和纠错工具。
    
    核心问题：每一次工具调用是否受到身份和权限约束。
    

讲解时可以说：

早期 Text-to-SQL 主要研究自然语言到 SQL 的转换准确性。

随着数据库规模增大，系统开始引入 Schema 检索、业务语义和 RAG，让模型能够获取更加相关的上下文。

进一步发展后，模型可以自主调用数据库工具，进行多轮查询和纠错。

这提高了系统能力，但也增加了工具权限、上下文污染和多轮调用的攻击面。

因此，我们的研究对象不只是 SQL 生成准确率，而是完整的自然语言数据库访问链路。

这里可以引用 2025 年的 Text-to-SQL 综述：

- Next-Generation Database Interfaces: A Survey of LLM-based Text-to-SQL
- P2SQL 论文

## 2. 补充 PostgreSQL 权限机制的原理对比

这个方向特别值得准备，因为老师很可能问：

既然 PostgreSQL 已经有权限管理了，为什么还需要额外开发 SQL Gateway？

可以准备以下一页备用 PPT。

| 机制 | 控制粒度 | 实际作用 |
| --- | --- | --- |
| Authentication | 用户/连接 | 确认连接身份 |
| RBAC | 角色、表、操作 | 决定允许哪些数据库操作 |
| RLS | 行 | 决定哪些记录可见 |
| Column Privileges | 列 | 决定哪些字段可访问 |
| Read-only Transaction | 事务 | 阻止写操作 |
| SQL Gateway | SQL 语句及业务策略 | 执行前解析、授权、阻断和审计 |

讲解词：

PostgreSQL 的权限机制已经非常完善，但它主要解决数据库层面的访问控制。

例如，RLS 可以限制学生只能读取自己的成绩；列级权限可以限制学生读取证件号码。

但是，数据库并不知道模型为什么生成这条 SQL，也不知道用户原本想查询什么。

SQL 网关的作用是把业务身份和 SQL 语句联系起来，在 SQL 执行之前进行确定性检查。

例如，模型生成了 DELETE，网关可以明确返回 NON_READ_ONLY；模型访问敏感字段，网关可以返回 COLUMN_DENIED。

数据库权限则继续作为最终兜底。

两者不是替代关系，而是不同层次的安全控制。

## 3. 补充 OWASP LLM 安全风险分类

可以参考 OWASP Top 10 for LLM Applications，增加一个学术与行业安全标准的参考页。

重点关联：

| OWASP 风险 | 本项目对应问题 |
| --- | --- |
| LLM01 Prompt Injection | 直接和间接提示词注入 |
| LLM02 Sensitive Information Disclosure | 敏感数据泄露 |
| LLM05 Improper Output Handling | 不可信模型输出直接进入执行链 |
| LLM06 Excessive Agency | 模型工具和数据库权限过大 |
| LLM08 Vector and Embedding Weaknesses | 未来扩展 RAG 时的检索污染风险 |
