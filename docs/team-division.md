# 三人小组分工与协作说明

## 1. 分工原则

本项目不是简单的三块代码拼接，而是“模型服务、攻击实验、安全防御、汇报材料”四条工作线的整合。每个人都有一个主责方向，同时必须理解完整链路并参与最终联调。所有实验结论必须有代码、日志或截图作为证据，不能只依赖口头描述。

`Pre` 汇报由成员 C 主责，视为一项与核心开发同等甚至更大的工作量。成员 A、B 仍需提供自己的技术材料并参加演练，不能将汇报准备全部转交给 C。

## 2. 成员 A：AI SQL 服务负责人

### 主要目标

完成“自然语言请求到候选 SQL”的本地模型链路，并分析大模型在数据库场景中的可靠性和安全风险。

### 具体任务

- 调研并确定 Ollama 本地模型，记录模型版本、运行方式和资源需求。
- 设计系统提示词，明确模型只能生成 SQL，不能自行执行 SQL。
- 编写自然语言请求、Schema 上下文和用户身份信息的组装逻辑。
- 实现统一的模型调用接口、超时处理和错误处理。
- 设计正常查询基线，例如查询个人课程、成绩和课程信息。
- 记录语法错误、字段猜测错误、权限理解错误和拒答情况。
- 配合成员 B 构造直接 Prompt Injection 和间接 Prompt Injection。
- 为前端提供原始请求、生成 SQL、模型响应和错误信息。

### 交付物

- Ollama 调用模块和配置示例；
- 系统提示词版本记录；
- 正常查询测试集；
- 模型生成成功率和错误案例表；
- 关于“提示词防御局限”的汇报材料。

### 验收标准

模型服务可以在本地运行；生成结果不会直接连接数据库；模型失败或输出非 SQL 时能安全返回错误；所有模型调用不依赖外部云服务。

## 3. 成员 B：数据库与攻击研究负责人

### 主要目标

建立可复现的 PostgreSQL 校园教务环境，负责攻击案例、真实背景调研和安全影响分析。

### 具体任务

- 设计 `students`、`courses`、`enrollments`、`grades`、`scholarships` 等表。
- 编写合成数据、数据库初始化脚本和重置脚本。
- 创建学生、教师、管理员和只读应用角色。
- 配置视图、最小权限和可用于对比实验的权限差异。
- 设计三类正式攻击：敏感字段越权、Prompt Injection、危险 SQL。
- 为每类攻击准备正常请求、攻击请求、预期结果和复现步骤。
- 搜集真实或典型应用场景，重点分析数据库对象、攻击面和传统机制失效原因。
- 记录攻击成功率、泄露字段、危险操作和对应证据。
- 协助成员 C 验证安全网关是否真正阻断攻击，而不是仅由模型拒答。

### 交付物

- PostgreSQL 建表、角色和种子数据脚本；
- 威胁模型和攻击案例文档；
- 攻击测试样例及预期结果；
- 攻击前后 SQL、日志和截图；
- 汇报中的案例背景与安全影响部分。

### 验收标准

任何成员都能从空数据库重复建立实验环境；测试数据不包含真实个人信息；每个攻击都有明确前提、影响、复现命令和防御后的对照结果。

## 4. 成员 C：安全网关、评估与 Pre 汇报负责人

### 主要目标

实现模型输出后的独立安全控制，并负责把三人的工作整合为可演示、可解释的 Pre 汇报。

### 具体任务：安全实现

- 实现 SQL 解析和语句类型检查。
- 拦截多语句、非白名单语句、注释绕过和危险关键字。
- 实现表级、字段级和用户级访问策略。
- 检查查询返回行数，处理手机号、身份证号等敏感字段脱敏。
- 接入 PostgreSQL 只读角色和只读事务。
- 记录用户身份、请求摘要、SQL 摘要、安全决策和拦截原因。
- 编写允许、脱敏和阻断三类测试。

### 具体任务：实验评估

- 建立“无防御、仅提示词、提示词加安全网关”三组实验。
- 统计拦截率、泄露率、误拦截率、SQL 正确率和响应时间。
- 检查实验结果是否能由日志和测试重新得到。
- 统一三人的结果格式，维护最终实验表格。

### 具体任务：Pre 汇报主责

- 制定汇报叙事：问题背景、攻击面、攻击演示、防御设计、实验结论。
- 设计 10 分钟以内的时间分配和页面顺序。
- 制作 PPT、系统架构图、攻击链路图和结果对比表。
- 设计现场演示脚本，包括成功路径、失败路径和备用录屏。
- 组织至少两次全流程演练，记录超时、模型不稳定和环境问题。
- 统一术语，检查报告、PPT、代码行为和实验数据是否一致。
- 准备老师可能提问的问题，例如“为什么不能只依靠 PostgreSQL 权限”“为什么提示词不是安全边界”“SQL 网关是否可能误报”。

### 交付物

- SQL 安全网关；
- 安全回归测试和指标统计脚本；
- 最终实验结果表；
- PPT、演示脚本、备用录屏和答辩问题清单；
- 最终提交前的完整检查清单。

### 验收标准

攻击请求能够被安全网关稳定识别或阻断；所有结论有实验数据支持；Pre 可以在 10 分钟内完整演示，且即使 Ollama 临时失败也能使用录屏或固定结果完成展示。

## 5. 共同协作责任

- 成员 A 必须审阅模型调用和提示词部分的安全结论。
- 成员 B 必须审阅数据库权限、攻击前提和案例描述。
- 成员 C 必须审阅安全策略、指标和汇报一致性。
- 每周至少进行一次端到端联调：Web 输入、模型生成、网关决策、数据库结果和审计日志全部走通。
- 每个人至少提交一项测试或实验记录，避免只有一个人掌握运行方法。
- 发现安全策略、数据库结构或接口发生变化时，必须同步更新文档和演示脚本。

## 6. 阶段安排

| 阶段 | 成员 A | 成员 B | 成员 C |
|---|---|---|---|
| 第 1 阶段：方案与环境 | 模型调研、接口草案 | 数据库和角色设计 | 网关规则草案、汇报提纲 |
| 第 2 阶段：基线 | 正常 SQL 生成 | 建库、种子数据、攻击样例 | 基线执行和日志格式 |
| 第 3 阶段：防御 | 提示词防御 | 权限与攻击复现 | 网关、脱敏、审计和测试 |
| 第 4 阶段：评估 | 模型结果整理 | 攻击结果整理 | 指标统计、PPT 和完整演练 |

最终提交前，三人共同确认：代码可以从干净环境启动，实验数据可复现，汇报中的每个数字都能追溯到测试结果。
